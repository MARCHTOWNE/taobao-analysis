# 展示讲解要点（约 3 分钟）

## 一句话版本

用淘宝一亿条用户行为数据，做了从 MySQL 清洗分析、PySpark 全量特征工程到购买预测和用户分群的完整流程，并用规则基线和诊断实验说明了模型提升有限的原因。

## 三分钟讲法

1. **数据与目标（20 秒）**：一亿条行为日志，9 天，只有“谁在什么时候对哪个商品做了什么”，没有价格和用户画像。目标是回答业务问题，并预测用户是否会再购买。
2. **SQL 分析（60 秒）**：挑两三个最有代表性的结论讲，比如：购买高峰在上午 10 点、浏览高峰在晚上 9 点；很多购买是直接发生的，并不经过收藏或加购；12 月 2–3 日访问用户数明显上升。每个结论都有一张图和一条对应的 SQL。
3. **工程取舍（30 秒）**：MySQL 处理 5% 样本，全量交给 PySpark；MySQL 默认缓冲池只有 128MB，调到 8GB 后查询从几分钟降到几秒；SQL 在 DuckDB 上交叉验证过。
4. **预测与诊断（60 秒）**：按时间向前、用户不重叠的方式评估，对照规则基线。结果是梯度提升树 PR-AUC 0.404，规则基线 0.375，提升很小。诊断显示没有泄露、也没有过拟合，是行为汇总特征的信息本身有限，加上测试窗口恰好是流量上升期。
5. **分群与局限（10 秒）**：分成 4 类用于描述用户，轮廓系数偏低，所以只当描述工具。

## 可能被问到的问题

**为什么用 MySQL 又用 PySpark？** MySQL 负责 SQL 业务分析，是岗位里最常见的技能；全量 1 亿行在 MySQL 里太慢，所以全量特征工程交给 Spark。并不是为了堆技术栈，两者对应的是不同规模的任务。

**模型为什么提升这么小？** 做了诊断：同期的新用户 AUC 也只有 0.63，说明现有特征本身信息有限；测试窗口的整体购买率更高，使区分变难。没有用实验证明因果，只说是数据现象和推断。

**怎么避免数据泄露？** 两层：训练和测试按时间切分，测试标签都在训练标签之后；用户按哈希分组，测试用户不出现在训练里，并用“同批用户”对照验证了这一点。

**你自己做了哪些验证？** SQL 在 MySQL 和 DuckDB 上结果一致；Spark 特征在 5% 样本上与 DuckDB 独立重算的结果逐用户一致（全量没有逐用户对照）。

**如果有更多时间会做什么？** 做“用户-商品对”级别的预测（加购召回），补充每日序列和最近几小时的行为特征，对比 LightGBM 并做超参搜索，在更长时间的数据上验证。

## 不要说的话

- 不要说模型“预测准确”或“效果很好”，应说“比基线有小幅提升”。
- 不要把样本里的购买率、转化率说成平台整体水平。
- 不要说促销导致了 12/02–12/03 的上升，只说“该时段明显上升”。
